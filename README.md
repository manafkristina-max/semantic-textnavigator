# Semantic TextNavigator

Локальное приложение, которое по TXT-документам договоров поставки показывает **действующие на дату проверки**
сумму и срок поставки — с дословной цитатой, именем файла и абзацем для каждого значения.

## A. Обзор

**Пользователь:** специалист по закупкам, проверяющий действующие условия договоров.

**Проблема:** условия договора «размазаны» по договору, допсоглашениям, проектам и письмам. Чтобы ответить
«какой срок действует сейчас», нужно вручную понять, какой документ подписан, вступил ли он в силу и какие пункты меняет.
Ошибка — применить проект или письмо, перепутать аванс с суммой или срок оплаты со сроком поставки.

**Что делает MVP:**
- загружает несколько TXT (UTF-8, UTF-8 BOM, Windows-1251), определяет тип документа и признак подписания по содержимому;
- связывает допсоглашения, проекты и письма с договором по номеру в тексте (не по имени файла);
- извлекает поставщика, сумму и срок поставки, применяет только подписанные обеими сторонами и вступившие в силу допсоглашения;
- показывает сводную таблицу, карточку договора, несогласованные предложения и предупреждения;
- по кнопке «Показать источник» открывает абзац документа с подсветкой и техническую проверку цитаты;
- отвечает на четыре готовых вопроса, рассчитывая ответ из текущих документов.

**Границы MVP:** только TXT; поля — поставщик, сумма, срок поставки; формулировки — близкие к учебному набору;
без LLM, без БД, без авторизации; проверка подписи — только текстовый признак.

## B. Запуск

Требуется Python 3.11+ (проверено на 3.13; на 3.14 зависимости Streamlit могут не собираться).

```bash
./run.sh
```
Скрипт при первом запуске создаст `.venv`, установит `requirements.txt` (streamlit, pytest) и откроет сервер
на http://localhost:8501. Вручную:

```bash
python3.13 -m venv .venv && .venv/bin/pip install -r requirements.txt
```
```bash
.venv/bin/python -m streamlit run app.py
```

**Пример:** вкладка «1. Загрузка» → перетащите TXT-файлы (или оставьте галочку «Использовать документы из папки documents»)
→ дата проверки (по умолчанию 10.03.2026) → «Проанализировать».

**Тесты:**
```bash
./run.sh test
```

**Остановка:** `Ctrl+C` в терминале, где запущен сервер.

Во время разработки страница обновляется автоматически после сохранения кода (`.streamlit/config.toml`, `runOnSave`);
загруженные файлы хранятся в сессии и не теряются при перезагрузке кода.

## C. Архитектура

```
TXT ─► loader ─► classifier ─► linker ─► extractors ─► rules ─► AnalysisResult ─► app.py (UI)
        │            │             │           │            │                     ├ сводная таблица
   кодировка,   тип, подпись,  номер     FieldSpec-реестр  правила на дату        ├ карточка + источник (evidence.py)
   абзацы p<N>  дата вступл.   договора  + Evidence        проверки               └ вопросы (questions.py)
```

| Шаг | Где | Что делает |
|---|---|---|
| Загрузка | `navigator/loader.py` | декодирование, отказ от пустых/нечитаемых файлов, абзацы с id `p<номер строки>`, id документа = хэш содержимого |
| Классификация | `navigator/classifier.py` | тип по заголовку; «подписан обеими сторонами» с учетом отрицаний; дата «вступает в силу» |
| Связывание | `navigator/linker.py` | номер договора в тексте; несколько номеров → «неоднозначно», не связываем |
| Извлечение | `navigator/extractors.py` | реестр `FIELD_SPECS`: формулировки условия, формулировки изменения, нормализация |
| Бизнес-правила | `navigator/rules.py` | действующие значения, первоначальные значения, предложения, конфликты, статусы |
| Навигация к источнику | `navigator/evidence.py`, `app.py` | проверка, что цитата дословно есть в абзаце; подсветка фрагмента; показ документа с выделенным абзацем |

Статусы значения: **Подтверждено** / **Нет данных** / **Требуется проверка**; предложения хранятся отдельно (`PendingProposal`)
и никогда не подменяют действующее значение.

## D. Три ключевых решения

**1. Детерминированные правила вместо LLM.**
Почему: главное требование — нулевая выдумка и проверяемость; регулярные выражения с контекстом дают воспроизводимый
результат, цитату и объяснимую причину. Работает офлайн, бесплатно, тестируется pytest.
Недостатки: чувствительность к формулировкам; новые обороты требуют новых шаблонов.
Пересмотр: при разнообразных реальных договорах — LLM как *кандидатогенератор* (предлагает фрагмент), а правила и проверка
цитаты остаются валидатором; принимается только значение, дословно найденное в тексте.

**2. Допсоглашение меняет только явно изложенные пункты.**
Почему: так устроено право — «Пункт 2.1 изложить в следующей редакции: «…»». К новой редакции пункта применяются те же
правила, что к договору, поэтому логика извлечения не дублируется.
Недостатки: не поддерживаются косвенные изменения («цена увеличивается на 15%»).
Пересмотр: появление таких формулировок → отдельный тип изменения с расчетом и обязательной ручной проверкой.

**3. Консервативные статусы вместо «лучшей догадки».**
Почему: ошибка «показали неверный срок» дороже, чем «попросили проверить». Неизвестная подпись, нет даты вступления
в силу, противоречивые соглашения с одной датой → «Требуется проверка».
Недостатки: больше ручной работы на «грязных» документах.
Пересмотр: после накопления статистики ручных проверок — смягчать правила там, где они систематически перестраховываются.

## E. Продуктовая записка

**Целевой пользователь:** специалист по закупкам, который перед приемкой, оплатой или претензией проверяет действующие условия.

**JTBD:** «Когда мне нужно принять решение по поставке, я хочу за минуту увидеть действующие сумму и срок с основанием,
чтобы не применить по ошибке неподписанное изменение».

**Пять вопросов клиенту:**
1. Какие форматы и типы документов приходят на практике (PDF-сканы, DOCX, ЭДО, спецификации, приложения)?
2. Какое правило считается юридически достаточным для «подписан»: отметка ЭДО, ЭП, скан с подписями, статус в учетной системе?
3. Сколько договоров и документов обрабатывается в месяц, сколько изменений на договор, как часто нужен пересчет?
4. Откуда берутся документы и куда отдавать результат (СЭД, ERP/1С, почта, ЭДО)?
5. Какая метрика успеха важна бизнесу: время проверки, число претензий из-за ошибок в сроках, штрафы, доля автопроверки?

**Допущения MVP:** текстовая отметка «подписано обеими сторонами» принимается как признак подписания (не верификация);
дата вступления в силу должна быть явно указана; номер договора имеет вид `БУКВЫ-цифры`; одна редакция пункта —
одно значение; дата проверки по умолчанию 10.03.2026.

**Метрика качества извлечения — точность подтвержденных значений.**
Определение: доля значений со статусом «Подтверждено», совпадающих с эталонной ручной разметкой.
Измерение: размеченная выборка (≥ 100 договоров), автоматический прогон в CI; целевое значение ≥ 99%,
параллельно отслеживается доля «Требуется проверка» (полнота автоматизации).

**Метрика пользовательской ценности — время до ответа о действующих условиях.**
Определение: медианное время от загрузки пакета документов до фиксации ответа по договору.
Измерение: событийная аналитика в UI (загрузка → открытие карточки/источника → отметка «проверено») против базового
замера ручной проверки; цель — сокращение в 3+ раза.

## F. Масштабирование (100 000 документов и роли)

- **Асинхронная обработка:** загрузка возвращает id задачи; воркеры извлекают условия; UI получает статус.
- **Очередь задач:** брокер (RabbitMQ/Redis/SQS), идемпотентные задачи по хэшу содержимого (он уже является id документа).
- **Хранение:** оригиналы в объектном хранилище (неизменяемые версии), метаданные, абзацы, термины и evidence — в PostgreSQL.
- **Поисковый индекс:** OpenSearch по абзацам с полями «номер договора», «тип», «статус» — для навигации и поиска по корпусу.
- **Инкрементальность:** при новом документе пересчитывается только связанный договор; при изменении правил — переобработка
  по версии экстрактора.
- **Права доступа:** ACL на уровне документа; результат (таблица, ответ, цитата) фильтруется по правам пользователя —
  нельзя показать цитату из документа, к которому нет доступа, даже косвенно через «действующее значение».
- **Журнал аудита:** кто загрузил, какая версия правил дала значение, кто подтвердил/переопределил вручную.
- **Мониторинг качества:** доля «Требуется проверка», расхождения с ручными правками, дрейф формулировок, выборочная разметка.

## G. Три следующих улучшения

1. **Ручное подтверждение и комментарий к «Требуется проверка»** — закрывает цикл работы закупщика, дает разметку для метрики качества.
2. **Загрузка DOCX/PDF с текстовым слоем** — снимает главный барьер реального использования.
3. **Новые поля: неустойка, условия оплаты, график поставок по партиям** — расширяет ответ на вопрос «что будет при просрочке».

## H. Известные ограничения

- Извлечение зависит от формулировок, близких к учебному набору; произвольные юридические обороты могут дать «Нет данных».
- Не поддерживаются косвенные изменения («увеличить на 10%»), относительные сроки («через 30 дней после оплаты») —
  они не превращаются в дату, а дают «Нет данных».
- Подлинность подписи по TXT не проверяется: распознается только текстовая отметка.
- Только TXT, один договор на файл; размер ограничен настройками Streamlit (200 МБ на файл).
- Договор без номера в заголовке не попадает в таблицу (выводится предупреждение).
- Суммы прописью не сверяются с цифрами.

## I. Отчет о вайбкодинге

**Инструмент:** Claude Code (desktop, модель семейства Claude), работа в одной сессии: анализ документов, код, тесты,
запуск и проверка UI во встроенной браузерной панели.

**Характерные запросы:**
1. Мастер-промпт с ТЗ: роли, бизнес-правила, 14 тестовых сценариев, требования к цитатам и документации.
2. «Начинай с изучения реальных документов… создай и проверь приложение».
3. Режим live coding: «после каждого изменения — тесты, перезапуск, проверка в браузере, отчет в формате Реализовано/Проверено/Приложение/Ограничения».

**Реальные ошибки AI и как они найдены:**
- В первой версии UI результат анализа (объекты dataclass/Enum) хранился в `st.session_state`. При горячей перезагрузке кода
  Streamlit пересоздает классы, и сравнения `status is ValueStatus.CONFIRMED` перестали бы работать. Обнаружено при самопроверке
  кода до первого запуска; исправлено — в сессии храним исходные файлы и дату, анализ пересчитывается.
- Тест на пустой/нечитаемый файл содержал условие с `or`, которое проходило всегда. Обнаружено при ревью после «подозрительно»
  зеленого прогона; ассерт ужесточен.
- Формулировка ответа «по Доп. соглашение № 1» — найдено на смоук-прогоне, исправлено на «основание: …».

**Как проверено, что тесты действительно ловят ошибки:** правило «неподписанные документы не применяются» временно отключено —
упали 5 тестов; код восстановлен, прогон снова зеленый.

**Проверено тестами:** все 14 обязательных сценариев + компоненты (кодировки, отрицания подписи, неоднозначные связи,
нормализация) + сквозной сценарий UI через `streamlit.testing.AppTest`. Вручную (в браузерной панели): загрузка 6 документов,
сводная таблица, карточка STN-101 и переход к абзацу p6 допсоглашения.
